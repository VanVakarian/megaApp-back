# 43. Улучшение ранжирования поиска еды

## Цель

Нужный продукт — выше, непохожий — ниже. Без новых зависимостей, без нагрузки на сервер, поиск остаётся мгновенным.

## Текущая архитектура

- Каталог ~456 товаров. У каждого вектор имени и вектор описания (OpenAI small, 768 измерений) в SQLite.
- Фронт шлёт запрос по WebSocket на каждый символ, показывает результат из клиентского кэша мгновенно и затем заменяет ответом сервера.
- Сервер: вектор запроса (OpenAI, кэш в таблице) → баллы: набор текстовых правил по подстроке в названии, старом названии и описании плюс косинус → сортировка, ничья решается по алфавиту.
- Векторы каталога на каждый промах кэша читаются из SQLite и декодируются заново.
- Исправление раскладки выполняется на сервере только внутри текстового скора. Вектор запроса строится по исходному тексту, поэтому для «ifehvf» в OpenAI уходит бессмыслица и сохраняется в таблицу (881 латинская запись из 10 546).

## Найденные проблемы

- Многоуровневая система баллов из текстовых правил плохо согласована с вектором: слабое текстовое совпадение проигрывает шуму вектора.
- Совпадение по подстроке в любом месте слова даёт ложные попадания, морфология не учитывается.
- ё и е считаются разными буквами («хлеб чёрный» не находит «Хлеб черный»).
- Каждый запрос тянет все векторы из БД, декодирует и пересчитывает нормы.
- Забытая раскладка порождает бессмысленные запросы к OpenAI и мусорные ключи во всех кэшах.
- При сбое OpenAI поиск по новому запросу не возвращает ничего, тогда как текстовые результаты были бы доступны.

## Решение

### Ранжирование: одна формула

Оценка товара = сходство вектора запроса с векторами товара + одна плоская поправка за текст.

- Сходство: косинус с вектором имени и вектором описания, пополам, как сейчас. Это основа ранжирования.
- Поправка: плоская, одной величины. Если хотя бы одно слово запроса является началом хотя бы одного слова в названии товара — оценка повышается. Если ни одно слово запроса не является началом слова в названии — понижается. Повышение и понижение одной величины.
- Никаких степеней: два совпавших слова не дают больше, чем одно. Точное совпадение названия отдельно не учитывается.
- Совпадение «в начале слова» понимается с грубым стеммингом без словаря: у слова запроса отрезается конец, и проверяется, начинается ли слово названия с остатка. Слова от шести букв — отрезаются две буквы, от четырёх до пяти — одна, до трёх букв — не режутся. Так «яблоко» находит «Яблоки», «сметана» — «со сметаной», «яйцо» — «яйца». Без этого полное слово в другой форме ошибочно получало бы понижение. Синонимы («картошка» и «картофель») стемминг не связывает, это задача вектора; изредка находит лишнее родственное слово («молоко» и «молочный»), что допустимо, потому что поправка плоская и товар не выбрасывается. Длины отреза подбираются тестами на реальных запросах.
- Только название. Старое название и описание в серверном ранжировании не участвуют: за них отвечает вектор.
- Слово внутри другого слова («моло» в «кисломолочный») поправки не получает, но и не выбрасывается: товар остаётся выше или ниже по сходству вектора, с понижением.
- Кандидат — товар с совпадением в начале слова или с положительным сходством. Товар без совпадения и с неположительным сходством не показывается. Порога схожести сверх этого нет.
- Выдача: лучшие 30 по оценке.
- Ничья по оценке — по алфавиту.
- Величина поправки — одна константа, 0,15. Подобрана по реальным популярным запросам из копии боевой БД: при 0,10 и выше первым результатом всегда оказывается товар с совпадением в названии (при 0,05 промахивается несколько запросов, без поправки — 58 из 414). Значение с запасом, но не превращает ранжирование в жёсткие уровни: близкий по вектору товар без совпадения всё ещё может обойти далёкий с совпадением.
- Если вектор запроса получить не удалось (сбой OpenAI, таймаут), сходство у всех нулевое; выдаются только товары с повышением (совпадение в начале слова), остальные не показываются. Сбой логируется, ошибка пользователю не уходит.

### Исправление раскладки — на фронте, до всего остального

Термин: «исправление раскладки» (конвертация раскладки, как в Punto Switcher). Не транслитерация: буквы заменяются по положению клавиш, «ifehvf»→«шаурма».

Принцип: английских названий в каталоге нет, значит латиница в запросе всегда означает забытую раскладку. Фронт исправляет её с первого же символа, и дальше по всей системе существует только русский запрос. Сервер раскладку не знает.

- Правило: если в запросе нет кириллицы и есть латинские буквы, весь запрос конвертируется по таблице клавиш. Смешанный ввод не меняется.
- Знаки на клавишах русских букв (запятая, точка, точка с запятой, апостроф, скобки, тильда) становятся буквами, кроме знаков между цифрами («2,5» остаётся числом).
- Единая точка входа — сервис каталога на фронте. Она находится после разбора веса («молоко 200» отрезается раньше), и перед ней стоит задержка, поэтому она покрывает все вызовы поиска: поле выбора продукта, форму правки продукта.
- Исправленный текст используется везде: ключ клиентского кэша, текст запроса к серверу, сопоставление ответа с введённым. В поле ввода пользователь видит свой исходный текст.
- Клиентский кэш помогает и при забытой раскладке: «vjkjrj» сразу находит закэшированное «молоко».
- Локальный поиск по старым названиям на фронте использует ту же функцию. Прежний двойной проход (исходный текст и исправленный) заменяется однократным исправлением.
- Таблица клавиш на фронте остаётся одной, с клавишей ё. Серверная копия таблицы и весь серверный код раскладки удаляются.
- Следствие: запросы на английском («burger») больше не находят ничего. Это принятое решение: английских названий в каталоге нет.
- Следствие для кэшей: ключи «ifehvf» в таблице векторов больше не создаются. Накопленные латинские записи безвредны и не используются.

### Нормализация на сервере
- Для сопоставления слов запрос и названия приводятся к нижнему регистру, ё→е, слова режутся по любым знакам кроме букв и цифр («(молоко/вода)» даёт «молоко» и «вода»).
- Ключ кэша векторов запросов и текст, уходящий в OpenAI, сохраняют ё: нижний регистр и схлопнутые пробелы. Так остаются рабочими десять тысяч уже сохранённых векторов, а модель получает слово как оно написано.
- Ключ кэша результатов в снимке — тот же нормализованный запрос.

### Индекс в памяти
- Неизменяемый снимок: слова названий, векторы, приведённые к единичной длине (косинус = скалярное произведение), флаг архива.
- Кэш результатов поиска живёт внутри снимка и исчезает вместе с ним. Отдельной очистки кэша результатов нет.
- Строится лениво при первом поиске после сброса. Параллельные поиски не строят его дважды.
- Поиск не ходит в SQLite за векторами.

### Инвалидация
Вся логика — одно правило: любое изменение каталога сбрасывает снимок целиком; следующий поиск строит новый. Каталог маленький, пересборка занимает миллисекунды.

- Единая точка «каталог изменился» в сервисе. Она сбрасывает и кэш каталога, и индекс. Все места записи обязаны её вызывать.
- Места записи:
  - Сохранение товара: создание, правка названия, описания, КБЖУ, вектора и архивация.
  - Удаление товара.
  - Лабораторные операции: генерация описаний, пополнение векторов, полная очистка каталога, импорт. Сейчас они не сбрасывают ни кэш каталога, ни кэш результатов, поэтому результаты поиска после них устаревают. Переводятся на ту же точку.
- Гонка «сброс во время сборки»: сборка идёт под замком, а сброс ждёт её окончания и затем убирает готовый снимок. Снимок, прочитавший каталог до записи, не переживёт сброс этой записи.
- Поиск, начатый до сброса, дописывает результат только в свой старый снимок, который уже никто не использует. Устаревшие результаты в новый кэш не попадают.
- Изменения БД в обход сервера (ручные SQL-правки из каталога `data-fixes`) работающий сервер не видит. Как и сейчас для кэша каталога, после них нужен рестарт.

### Задержка ввода на фронте
- Показ результата из клиентского кэша остаётся мгновенным на каждый символ.
- Отправка на сервер откладывается примерно на 200 мс после последнего символа и покрывает все места вызова серверного поиска. Очистка при пустом поле — без задержки.
- Legacy-поиск локальный, без сервера, задержки не получает.

### Legacy-поиск на фронте (не затрагивается)
- Отдельная цепочка целиком на фронте: переключатель в поле поиска, фильтр локального каталога по старому названию, без сервера, OpenAI и векторов. Серверное ранжирование ему не нужно.
- Изменения серверного поиска (формула, индекс, нормализация, удаление старого названия из ранжирования) на него не влияют.
- Поле старого названия остаётся в БД и в ответе каталога, его никто не удаляет: от него зависит этот режим.
- Единственное изменение — общая функция исправления раскладки на входе (вместо прежнего двойного прохода «исходный текст или исправленный»). Для русских старых названий результат тот же.
- Совпадение остаётся прежним: все слова запроса входят как подстрока в старое название. Стемминг и совпадение с начала слова к нему не применяются.

### Не меняется
- Модель и размер вектора.
- Таблица кэша векторов запросов (после рестарта серверу не приходится заново платить за популярные запросы).
- Протокол WebSocket: один ответ на запрос.
- Вес вектора имени и описания 50/50.

## Проверка

- Фронт: полная таблица клавиш; забытая раскладка находит нужный товар и по полному слову, и по набранному префиксу («ifeh»); «2,5» не портится; кириллица и смешанный ввод не меняются; ключ клиентского кэша и текст запроса — исправленные; в поле ввода остаётся исходный текст; задержка отправки не задерживает показ из кэша.
- Сервер, табличные тесты: нормализация; совпадение с начала слова со стеммингом; слово внутри другого слова не повышается; поправка одной величины для одного и нескольких совпавших слов.
- Сервер, инвалидация: после создания, правки, архивации и удаления товара, а также после лабораторных операций, поиск отдаёт свежие данные. Сброс во время сборки не публикует устаревший снимок.
- Сервер, отказ: при ошибке получения вектора запроса поиск возвращает товары с совпадением в начале слова.
- Существующий серверный тест забытой раскладки удаляется вместе с серверным кодом раскладки; его смысл переезжает в тесты фронта.
- Регрессионный набор: топ реальных русских запросов по популярности с ожидаемым товаром. Векторы запросов берутся из уже сохранённой таблицы, поэтому OpenAI не нужен. Запускается на копии боевой БД, без файла пропускается. По нему подбирается величина поправки.
- Метрика: позиция ожидаемого товара до и после.

## Эксперименты (отдельно, только после замера по регрессионному набору)

- Соотношение весов имя/описание.
- Отсечение слабой семантики: порог схожести или отставание от лучшего.
- Не считать вектор для запросов короче трёх символов.
- Урезание размера вектора.

## Идеи на будущее (сейчас не делаем)

- Переранжирование по частоте использования: повышающий коэффициент в той же формуле, по записям дневника за последний год. Цель: из «Молоко 2,5% / 1,5% / 3,2% / 6%» выше то, что реально едят. Сомнение: сходство по вектору непредсказуемо, поэтому подобрать подходящий небольшой коэффициент может не получиться. Вернуться, если после этого плана близкие по названию товары всё ещё идут не в том порядке.

## Находки после ревью (v-review:claude, 10.10.2026)

1. Цифры из числа дают повышение посторонним товарам
   - **Важность:** стоит поправить
   - **Как сейчас работает:** запрос и названия режутся на слова по любым знакам, поэтому «2,5» становится двумя словами «2» и «5». Товар повышается, если хоть одно слово запроса — начало хоть одного слова в названии.
   - **Что не так:** на запрос «молоко 2,5» повышение получает любой товар со словом на «5» или «2» — например «Пиво 5%». Он поднимается наравне с настоящим молоком и может обойти его по близости вектора.
   - **Как поправить:** не считать числа и обрывки чисел словами для повышения: проверять только слова из букв, либо склеивать число с десятичным разделителем в один токен и сравнивать целиком.
   - **Как будет работать после правки:** повышение за совпадение дают только настоящие слова; «2,5» не поднимает «Пиво 5%».

2. Результат без вектора запоминается как полноценный
   - **Важность:** мелочь, но стоит поправить
   - **Как сейчас работает:** если вектор запроса не получить, поиск идёт по названиям и результат не запоминается. Но если вектор получен и оказался непригодным (нулевой или битый в таблице), ошибки нет, и результат только по названиям запоминается как обычный.
   - **Что не так:** запрос, у которого в таблице лежит битый или нулевой вектор, до ближайшего изменения каталога отдаёт урезанный список и не пробует получить вектор заново.
   - **Как поправить:** считать непригодный вектор такой же неудачей, как сбой OpenAI: не запоминать результат, а лучше заменить битую запись новым вектором.
   - **Как будет работать после правки:** урезанный результат никогда не залипает, следующий поиск пробует снова.

3. Лабораторные записи векторов меняют версию каталога у клиентов
   - **Важность:** мелочь, но стоит поправить
   - **Как сейчас работает:** любая запись в каталог, в том числе пополнение векторов в лаборатории, вызывает общий сброс, который заодно увеличивает версию каталога для клиентов.
   - **Что не так:** векторы клиентам не отдаются, но после пополнения на N товаров при следующем подключении все клиенты видят новую версию и заново скачивают весь каталог.
   - **Как поправить:** разделить сброс: индексу поиска нужен сброс при любой записи, а версию для клиентов менять только когда изменилось то, что клиент видит.
   - **Как будет работать после правки:** пополнение векторов обновляет поиск и не заставляет клиентов перекачивать каталог.

4. Поле для подбора поправки есть только ради теста
   - **Важность:** мелочь, но стоит поправить
   - **Как сейчас работает:** величина поправки лежит в константе и копируется в поле индекса, чтобы регрессионный тест мог перебирать значения.
   - **Что не так:** в боевом коде появился второй источник значения, нужный только тесту.
   - **Как поправить:** передавать величину параметром в функцию поиска (тест подставляет свою, боевой код — константу).
   - **Как будет работать после правки:** поведение то же, в индексе нет лишнего состояния.

## Исправления по итогам подбора коэффициентов (10.10.2026)

Причина: в исходном решении выбрана плоская поправка, чтобы два совпавших слова не давали больше одного. Подбор показал, что на запросах из нескольких слов это ошибка: «белый хлеб» отдавал первым «Хлеб черный», потому что совпадение по одному слову «хлеб» уже давало полное повышение.

Что заменяет в исходном решении (разделы «Ранжирование» и «Проверка»):
- Плоская поправка с повышением и понижением → повышение за каждое слово запроса, которое является началом слова в названии. Слово считается один раз, сколько бы слов названия оно ни продолжало.
- «Никаких степеней» → степени есть: товар, содержащий больше слов запроса, обходит товар, содержащий меньше.
- Величина 0,15 → 0,25 за слово. Выдача не меняется во всём диапазоне 0,15…0,6; выбрана середина. Близкий по вектору товар без совпадения всё ещё может обойти далёкий с совпадением.
- Понижение за несовпадение убрано: порядок определяет только разница между товарами, поэтому «плюс за совпадение, минус за его отсутствие» и «плюс только за совпадение» ранжируют одинаково.

Не меняется: стемминг (те же длины отреза), вес имени и описания пополам, кандидат (совпавшее слово или положительное сходство), выдача 30 лучших, ничья по алфавиту. Без вектора запроса выше идёт товар с большим числом совпавших слов, затем по алфавиту.

Проверка: табличные тесты ранжирования дополнены случаями «два слова запроса побеждают более близкий товар с одним» и «товар со всеми словами запроса идёт раньше товаров с одним»; старый случай «два слова дают столько же, сколько одно» заменён. Регрессионный набор на копии боевой БД: при повышении 0,25 первым всегда стоит товар с совпадением (414 из 414; при 0,15 — 413), среднее число совпавших товаров в топ-5 — 3,78. Тест перебора сверяется с боевой функцией поиска на всех запросах (тест позже удалён, см. раздел о воспроизведении в конце).

## Нижняя граница сходства: эксперимент (10.10.2026)

Вопрос: есть ли порог сходства, ниже которого товар можно безопасно убрать из выдачи (запрос «пиво» без молока, «молоко» без мяса), не потеряв ничего подходящего.

Метод: те же размеченные запросы (180 законченных и 30 префиксов), выдача как в бою (30 лучших). Товары с совпавшим словом названия не отбрасываются никогда. Проверены границы: абсолютная по сходству; «лучшее сходство запроса минус d»; доля от лучшего; z-оценка внутри запроса по всему каталогу; просто более короткий список. Сигналы: среднее сходство (как в бою), сходство с названием, лучшее из двух. Для каждой границы найдено самое агрессивное значение без потери «точно того» (и отдельно без потери «близкого»), устойчивость проверена на половинах запросов: подбор на одной, проверка на другой.

Результат: надёжной границы нет.
- Безопасный максимум абсолютной границы по среднему сходству — 0,19; он убирает 0 % мусора. При 0,25 уходит 11 % мусора, но теряются 16 «близких» и 1 «точно то»; при 0,30 — 31 % мусора, но теряются 47 «близких» и 4 «точно то».
- Абсолютная граница не работает из-за разного масштаба сходства у разных запросов: у «молоко» мусор («Морковь») 0,43 при лучшем 0,64, у «торт» нужный «Тирамису» 0,29 при лучшем 0,35.
- Лучшая относительная граница — z-оценка 1,4 по лучшему из двух сходств: убирает 28 % мусора, «точно того» не теряет (и на проверочных половинах тоже), но теряет 44 из 802 «близких». Остальные относительные границы теряют «точно то» на проверочных половинах.
- Причина: в каталоге из 455 продуктов эмбеддинги не разделяют темы. «Пиво» → молоко 0,38, «Квас» (подходит) 0,36; «нектарин» → «Мандарины» (подходит) 0,20, «Нагетсы» (мусор) 0,26. Любая граница, убирающая молоко, убирает и квас.
- Короткий список хуже границ: топ-20 теряет 19 «точно то» из 452, потому что нужные товары стоят глубоко (95-й перцентиль места — 17, максимум — 30).

Решение: отсечение по нижней границе не делаем. Мусор стоит ближе к концу выдачи, «точно то» — в основном в первой десятке (медиана места — 2). Если понадобится убирать «пиво без молока», нужна структура (категория продукта или признак), а не сходство.

Эксперимент с нижней границей:
- Использует тот же набор и разметку; выдача строится как в бою (30 лучших), товары с совпавшим словом названия границей не отбрасываются.
- Три сигнала: среднее сходство (как в бою), сходство с названием, лучшее из двух. Четыре вида границ (абсолютная; лучшее сходство запроса минус d; доля от лучшего; z-оценка среди всех товаров каталога для запроса) и укороченный список (первые N мест).
- Для каждой границы перебор значений от мягкого к жёсткому; самое жёсткое значение без потери «точно того» и отдельно без потери «близкого»; сколько мусора ушло; сколько «близких»; запросы, оставшиеся с менее чем тремя товарами; потери на префиксах; проверка на половинах запросов (чётные/нечётные номера: значение подбирается на одной половине, потери считаются на другой).
- Дополнительные отчёты: распределение сходства по классам среди товаров без совпавшего слова (мин., перцентили, макс.); самые низкие по сходству «точно то» и «близкие» без совпавшего слова; список отброшенных товаров по выбранной границе для выбранных запросов; распределение мест «точно того», «близкого» и мусора в выдаче.
