# 41. Список транзакций следует графикам, категории управляют графиками (бэкенд)

Сквозной план из двух парных файлов с общей нумерацией: этот (бэкенд) и [фронтенд](../../megaapp-front/plans/41-money-transactions-linked-to-chart-categories.implementation-plan.md). Основная работа на фронте; бэкенд хранит новые свойства категорий и новые поля настроек. Общие разделы одинаковы в обоих, чек-листы свои.

## Цель

Две связанные вещи:
1. Переключатель в настройках экрана денег: список транзакций показывает только то, что питает отмеченные серии графиков расходов и доходов.
2. Графики не зависят от имён категорий, зашитых в код. Что скрыто на графиках, какого цвета серия и куда уходят подарки — свойства самой категории, редактируются в UI.

## Общие решения

- Фильтр списка только на фронте. Все транзакции целиком в памяти (снапшот без пагинации, на проде ≈4200), графикам и балансам нужны все. Серверная фильтрация и постраничная выдача исключены: ломают баланс-график и требуют дублировать правила серий на бэкенде.
- Режим списка — явный переключатель в серверных настройках денег, по умолчанию выключен. Выключен — полный список независимо от галочек. Включён — только транзакции, питающие отмеченные серии; всё прочее (переводы, транзакции скрытых категорий) пропадает осознанно.
- Список ведёт себя ровно как график: одна функция «транзакция → серия» на фронте обслуживает и построитель графиков, и фильтр списка.
- Подарок работает как раньше: расход с признаком подарка (галочка у транзакции) всегда идёт в серию расходной категории «Подарок» на графике и в списке. Это правило живёт на фронте и не требует ничего от бэкенда.
- Категория получает два свойства:
  - скрыта на графиках — серии у такой категории нет, ни включить, ни увидеть её на графике нельзя, в режиме списка её транзакции скрыты;
  - цвет — hue (оттенок 0–360) или пусто («авто»).
- Серии графика:
  - расходы: каждая не скрытая категория расходов + виртуальная серия «Uncategorized» (расход без категории);
  - доходы: каждая не скрытая категория доходов + виртуальные серии «Дивиденды», «ЦБ закрытые», «ЦБ открытые», «Крипта закрытые», «Крипта открытые».
- Отмеченные серии хранятся списком отмеченных id отдельно для расходов и доходов. Новая серия по умолчанию не отмечена, её включают галочкой под графиком.
- Иерархия категорий (родитель/потомок) остаётся в модели без изменений. Графики и фильтр её игнорируют, скрытость не наследуется потомками.
- Порядок серий на графиках остаётся зашитым списком имён на фронте (см. «Идеи на будущее» фронтенд-плана).

## Контракт бэкенд ↔ фронтенд

Категория (чтение, создание, правка), два новых поля:
- флаг «скрыта на графиках» — булево, по умолчанию false;
- цвет (hue) — целое 0–360 или null; вне диапазона — ошибка валидации (400).
- Правка категории по-прежнему заменяет запись целиком: фронт присылает все поля.
- Тип категории нельзя сменить, пока на неё ссылаются транзакции (409): серии графиков строятся по id категории и опираются на связь «тип категории = вид транзакции».

Настройки денег:
- убираются поля скрытых серий (два набора);
- добавляются: список отмеченных серий расходов, список отмеченных серий доходов (целые id; отрицательные — виртуальные серии в рамках своего графика; по умолчанию пустые) и булево «список транзакций следует графикам» (по умолчанию false);
- имена полей отмеченных серий: для расходов `enabledCategoryIds`, для доходов `incomeEnabledCategoryIds`; в сохранённом JSON настроек денег уже лежат ключи с этими именами и значениями — отмеченные категории от прежней версии настроек, которые ничего не читает. Они становятся начальным выбором владельца (расходы — почти все категории с данными, доходы — Зарплата, Проекты, Проценты, дивиденды и ряд серий бумаг); владелец поправляет выбор галочками под графиками. Очистка хранилища не нужна;
- `null` отклоняется как для любого небулевого поля, неизвестные поля — 400, как и раньше.

Снапшот денег: убирается список сделок с бумагами (`investAssetTrades`). Всё его содержимое выводится на фронте из самих транзакций и активов (идентификатор актива лежит в деталях транзакции, название/тикер/тип — у актива). Список транзакций и активов в снапшоте остаётся как есть. Отдельный эндпоинт списка сделок убирается: потребителей нет.

## Текущая реализация (бэкенд)

- Категория: таблица с названием, родителем, типом (доход/расход). Типизированные структуры чтения и входа; репозиторий читает и пишет четыре поля; сервис проверяет имя, тип, существование и тип родителя; удаление запрещено при потомках и привязанных транзакциях.
- Снапшот денег отдаёт категории тем же чтением, что и отдельный список. Отдельно в снапшот кладётся список сделок с бумагами (покупки и продажи с названием, тикером и типом актива) — тот же запрос внутри сервиса определяет, по каким тикерам отдавать историю котировок (какие бумаги держались на конец месяца); сам список дублирует транзакции и активы и фронту не нужен. Тот же запрос отдаётся отдельным эндпоинтом, который фронт не вызывает.
- Настройки денег — типизированная структура пакета настроек. Запись проверяет входные поля по белому списку (структура, неизвестное — 400, `null` для небулевых — 400), затем круговой разбор слитого JSON, терпимый к лишним ключам хранилища. Читаются сохранённые данные, слитые со значениями по умолчанию. Тест круговой записи/чтения настроек денег есть.
- Данные прода (копия 2026-10-02): 4166 транзакций, 694 с признаком подарка; категорий расходов 18, доходов 6; в хранилище настроек скрытые серии пусты.

## Разветвления и проверки

- Создание/правка категории с новыми полями — проходят и читаются обратно (список, снапшот).
- Вход без новых полей читается как false/null; правка заменяет запись целиком.
- Hue 0 и 360 допустимы, -1 и 361 — нет, null — «авто».
- Смена типа: у категории без транзакций проходит, с транзакциями — конфликт; правка без смены типа проходит всегда.
- Настройки: списки отмеченных серий сохраняются целиком, принимают отрицательные id и пустой список; `null` отказ; старые поля скрытых серий теперь неизвестные — отказ; хранилище со старыми ключами читается без ошибки.
- Существующие категории после миграции: скрытость false, hue пусто.
- Снапшот не содержит списка сделок с бумагами; отбор тикеров для истории котировок работает как раньше (внутренний запрос остаётся).
- Настройки со старыми ключами «включённых» категорий читаются как начальные значения полей отмеченных серий.

## Риски и допущения

- Фронт раньше бэкенда: сохранения отклоняются.
- Старый открытый клиент с новым бэкендом: его сохранение скрытых серий отклоняется (поле неизвестно), список сделок с бумагами в снапшоте пуст — серии «ЦБ/Крипта» пусты, пока вкладка не обновлена. Единственный пользователь, совместимость не держим.
- Начальный выбор серий берётся из устаревших значений в хранилище; новые серии и серии, которых там нет (например, «Uncategorized», «Крипта закрытые»), не отмечены. Владелец один раз просматривает легенду.
- Скрытость по умолчанию выключена: до шага 3 служебные категории (технический гэп и т. п.) числятся обычными.

4. Эталонные тесты ходят на удалённый маршрут сделок
   - **Важность:** стоит поправить
   - **Как сейчас работает:** маршрут списка сделок с бумагами убран. Эталонные тесты с копией прод-базы всё ещё запрашивают его и ждут 196 записей. Без файла эталонной базы эти тесты пропускаются, поэтому обычный прогон зелёный.
   - **Что не так:** там, где база есть, запрос вернёт «не найдено», проверка длины и параллельный прогон упадут. Заявление «все тесты зелёные» этих тестов не касалось.
   - **Как поправить:** убрать проверку сделок и адрес из параллельного прогона; проверять вместо них список транзакций. Прогнать эталонные тесты с базой.
   - **Как будет работать после правки:** эталонный набор не обращается к удалённому маршруту и проходит на машине с базой.

5. Смена типа категории ломает связь «тип категории = вид транзакции»
   - **Важность:** стоит поправить
   - **Как сейчас работает:** при записи транзакции тип категории сверяется с видом транзакции. При правке самой категории тип меняется без проверки привязанных транзакций.
   - **Что не так:** серии графиков и режим списка строятся по id категории. Если сменить тип категории с расходной на доходную, её расходы окажутся в доходной категории: «технический гэп», который миграция чинит разово, возникает заново.
   - **Как поправить:** запретить смену типа у категории с привязанными транзакциями (как уже запрещено удаление) с понятной ошибкой.
   - **Как будет работать после правки:** тип можно менять только у пустой категории, связь «тип = вид» не нарушается.
