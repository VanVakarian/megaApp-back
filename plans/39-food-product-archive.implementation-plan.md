# 39. Архивирование продуктов каталога (бэкенд)

Сквозной план из двух парных файлов с общей нумерацией: этот (бэкенд) и [фронтенд](../../megaapp-front/plans/39-food-product-archive.implementation-plan.md). Общие разделы (цель, решения, контракт, порядок выкатки, риски) одинаковы в обоих, чек-листы свои. Источник задачи: [план 37 (чистка каталога)](37-food-catalogue-cleanup.implementation-plan.md), этап 3.

## Цель

Админ может пометить продукт каталога архивным. Архивный продукт не находится поиском и не выбирается для новых записей, но остаётся в дневнике, статистике и личной калорийности с пометкой «архив». Инструмент чистки каталога: обобщённые продукты («Сладкая выпечка», «Конфеты») не склеиваем и не расклеиваем, а архивируем и заменяем новыми корректными.

## Общие решения

- Архив — обратимый признак продукта. Задаётся галочкой «Архивный» в форме правки продукта (между описанием и кнопками). Галочка видна только админу и только при правке существующего продукта (не при создании). По умолчанию у всех продуктов снята.
- Менять признак может только админ. Единственная защита — проверка на сервере; фронт лишь прячет галочку и не нагружается дополнительными проверками.
- Отдельной операции «архивировать» нет: признак сохраняется той же операцией сохранения продукта.
- Архивный продукт отдаётся клиентам в общем каталоге с признаком. Иначе в дневнике у старых записей пустые имена.
- Поиск: существующий серверный поиск получает режим «обычный / архивный». Обычный исключает архивные, архивный возвращает только архивные. Режим «архивный» применяется, только если он запрошен и пользователь админ; иначе всегда обычный (у не-админа параметр молча игнорируется).
- В пикере продукта у админа рядом с кнопкой «старого» поиска вторая кнопка «Архив»; режимы взаимоисключающие (старый поиск локальный, архивный серверный).
- Возврат из архива: админ включает режим «Архив», находит продукт, открывает его, «Редактировать», снимает галочку, «Сохранить». Архивный поиск, как и обычный, требует текст запроса; просмотр всего архива без запроса не делаем (архивных будет мало, при необходимости добавим позже).
- Блок статистики «История продукта» (выбор продуктов и просмотр, когда и сколько их ели) не меняем: пикер в режиме выбора для истории работает как раньше, кнопки «Архив» там нет, архивный продукт выбрать для истории нельзя. Решение пользователя (2026-10-02): ради одной функции логику не переделываем. На будущее: продумать отдельно, для истории важно видеть все продукты независимо от архива.
- Исключается из: обычного серверного и «старого» локального поиска, кэша результатов обычного поиска.
- Остаётся виден в: дневнике, статистике (топ продуктов), личной калорийности. Вернуть из архива может только админ.
- Новая запись дневника с архивным или несуществующим продуктом отклоняется обычной клиентской ошибкой, без особого кода и сообщения: случай редкий (устаревший каталог на клиенте), хватает перезагрузки страницы. Существующие записи можно менять и удалять; восстановление удалённого дня с архивными продуктами работает, но не создаёт записи с несуществующим продуктом.
- Удаление продукта как сейчас: только неиспользуемый (архивный неиспользуемый тоже можно удалить).
- Версия каталога поднимается при каждом сохранении (в том числе смене признака) и не обнуляется при рестарте сервера (закрывает остаточный риск плана 37, этап 1).

## Контракт бэкенд ↔ фронтенд

- Признак «архивный» присутствует в данных продукта везде, где они отдаются: весь каталог, один продукт, ответ сохранения, реалтайм-сообщение «продукт сохранён». Во всех местах контракта поле называется одинаково: `archived` (булево): в продукте, в запросе сохранения, в сообщении поискового запроса и в ответе поиска. Репозитории делаются независимо, имя фиксируем здесь.
- Сохранение продукта (существующая идемпотентная операция) получает необязательное поле «архивный». Нет поля — признак не меняется (старый фронт совместим). Не-админ, приславший поле с любым значением, получает отказ «запрещено» (403). Код 401 нельзя: по нему клиент разлогинивает пользователя. Фронт не-админа поле не отправляет вовсе.
- Каждое сохранение, как и раньше: сброс кэшей, подъём версии каталога, реалтайм «продукт сохранён» всем клиентам.
- Поиск по WebSocket: сообщение запроса получает необязательный признак «архивный режим»; ответ повторяет фактически применённый режим (чтобы ответ одного режима не показали и не сохранили как другой). Кто ищет, сервер определяет по пользователю сокета: роль проверяется в БД, только когда запрошен архивный режим. Результаты архивного режима не кэшируются ни на сервере, ни на клиенте (ищут редко).
- Ошибка создания записи с архивным или несуществующим продуктом — обычная клиентская ошибка валидации. Новых кодов и текстов на фронте нет: работает существующая общая обработка ошибок.

## Текущая реализация (бэкенд)

- Каталог общий, одна таблица. Правка и удаление доступны любому авторизованному пользователю; удалять можно только продукты без записей дневника.
- Весь каталог кэшируется в памяти вместе с версией. Версия растёт при сохранении и удалении, при рестарте сбрасывается в 0.
- Поиск идёт через одну общую точку: перебор кэша каталога + семантические оценки по эмбеддингам из БД; результаты кэшируются по тексту запроса. Через неё работает поиск по WebSocket; HTTP-вариант поиска фронтом не используется.
- Сокет знает пользователя, но не его роль; сервис авторизации умеет отдать пользователя по идентификатору (с флагом админа).
- Сохранение продукта: идемпотентно, сбрасывает кэш поиска и каталога; при правке чтение существующего продукта идёт до транзакции записи.
- Создание записи дневника не проверяет продукт (известная дыра: записи-призраки с пустым именем). Восстановление удалённого дня вставляет записи пачкой другим путём.
- Статистика, история продукта, личная калорийность и её ночной расчёт читают весь каталог, архивные включены: правок не нужно.
- В общей обвязке ошибок нет вида «запрещено».

## Чек-лист бэкенда

Схема:
- ✅ Новая миграция (000012, файл с датой в имени: 000012_2026-10-02_food_catalogue_archived;  последняя существующая 000011 уже применена на проде, править её нельзя): признак архива у продукта, по умолчанию «не архивный». Существующие продукты не меняются. В тестовой схеме таблицы каталога тоже добавить колонку.

Каталог:
- ✅ Все чтения продукта (весь каталог, один продукт, ответ сохранения) отдают признак; кэш каталога содержит архивные продукты.
- ✅ Отладочный экспорт каталога не теряет признак (проверено: он выгружает только имя и описание, признак не затрагивается; весь экспорт и импорт — в отложенном разделе служебных роутов).

Поиск:
- ✅ Общий поиск получает режим «обычный / архивный»: в цикле оценки пропускаются продукты не того режима, до обрезки по лимиту. Семантическая часть правки не требует (её оценки применяются только к записям из этого цикла).
- ✅ Решение о режиме в одном месте сервиса: архивный, только если запрошен и пользователь админ; иначе обычный. Роль берётся через небольшой интерфейс проверки админа, который реализует сервис авторизации (новый метод по идентификатору пользователя); без подключённой проверки все считаются не-админами.
- ✅ WebSocket: сообщение запроса принимает необязательный признак режима; роль пользователя проверяется через сервис авторизации по идентификатору (в БД, только при запросе архивного режима); ответ содержит применённый режим.
- ✅ HTTP-поиск не расширяем: остаётся обычным.
- ✅ Кэш результатов поиска используется только в обычном режиме; архивный его не читает и не пишет (кэш эмбеддингов запросов общий, не трогаем). Сброс при каждом сохранении продукта уже есть.

Дневник:
- ✅ Создание записи: продукт проверяется в той же транзакции, что и вставка, и после ветки идемпотентного повтора (повтор уже созданной записи не должен падать, если продукт потом заархивировали). Несуществующий и архивный → клиентская ошибка валидации.
- ✅ Восстановление дня: проверка существования продуктов (архивность не проверяется).
- ✅ Правка веса и удаление записей не затрагиваются.

Сохранение продукта:
- ✅ Необязательное поле «архивный»; не-админ с полем → «запрещено» в самом начале, до проверки идемпотентности и любых запросов.
- ✅ Запись признака одним запросом обновления (колонка меняется только если поле передано; без предварительного чтения), чтобы устаревшее чтение не перезаписало признак, выставленный параллельно. Нет поля → колонка не трогается. При создании по умолчанию «не архивный».
- ✅ Новый вид ошибки «запрещено» (403) в общей обвязке ошибок: две строки, фронт не затрагивает.

Версия каталога:
- ✅ Версия не обнуляется при рестарте: начальное значение — время запуска в миллисекундах.

Тесты и проверки:
- ✅ Табличные тесты: поиск в обычном режиме без архивных, в архивном только архивные; архивный режим от не-админа даёт обычный; архивный режим не читает и не пишет кэш результатов; создание записи (обычный, архивный, несуществующий продукт; повтор после архивации); восстановление дня (архивный продукт проходит, несуществующий нет); сохранение: админ меняет признак, не-админ с полем получает «запрещено» (и при том же значении), без поля признак сохраняется, создание по умолчанию не архивное; идемпотентный повтор; версия после рестарта.
- ✅ Сборка, статический анализ, все тесты проходят.
- ✅ Попутно: в сохранении продукта все чтения (проверка имени, существующий продукт) вынесены до открытия транзакции записи и до генерации эмбеддингов — транзакция держит только запись, внешний сервис не вызывается зря при отказе.

## Риски и допущения

- Запись, поставленная в офлайн-очередь до архивации продукта, после синхронизации будет отклонена (клиентские ошибки не повторяются) — пользователь увидит общую ошибку. Случай редкий (3 пользователя), принимаем.
- Права на правку и удаление продуктов не меняем (сейчас у любого авторизованного). Права только на признак архива — админ.
- Форма правки админа при открытии подтягивает свежий продукт; форма, открытая давно, может вернуть признак, изменённый параллельно. Принимаем.
- Имя продукта уникально, архивный продукт своё имя занимает: заменяющие продукты называть иначе либо сначала переименовать архивный.
- Допущения, подтвердить: (1) админ может править архивный продукт; (2) пометка «архив» в топе продуктов берётся фронтом из локального каталога, статистику бэкенда не меняем; (3) в топе продуктов архивные продукты показываются с пометкой.

## Отложено: служебные роуты только изнутри сервера

Не связана с архивом, добавлена по решению пользователя (2026-10-02). Решение пользователя: самый последний пункт, сейчас не разбираем и не делаем.

Найдено при беглом анализе, не разобрано дальше:
- Сейчас без авторизации открыты экспорт и импорт каталога; вместе они стирают каталог. Рекомендовалось блокировать эти пути в nginx не дожидаясь кода.
- Проверка источника запроса не должна опираться на адрес после глобального определения «реального IP»: заголовок True-Client-IP подделывается. Чище отдельный локальный листенер для служебных роутов.
- Фронтенд вызывает роут информации о коммите из группы debug: его нужно оставить открытым.
- Импорт каталога лучше удалить совсем, а не чинить.

Проблема: служебные роуты (lab и debug) зарегистрированы без авторизации и доступны из интернета (проверено 2026-10-02: безобидный запрос к одному из них вернул 200 с публичного адреса, в конфиге nginx ограничений нет). Опасные из них:
- импорт каталога стирает весь каталог и заново вставляет только имена и описания (ккал, БЖУ и эмбеддинги теряются, записи дневника теряют продукты); нужный для него файл создаёт открытый экспорт;
- сброс личной калорийности одному или всем пользователям, ручной запуск её расчёта;
- генерация продукта нейросетью с сохранением перезаписывает существующий продукт; генерация эмбеддингов и картинок тратит деньги на внешние сервисы;
- ручной запуск бэкапа.

Решение: как в проекте Flatline — служебные роуты доступны только изнутри сервера, вызываются по SSH на локальный адрес. Особенность: перед приложением стоит nginx, поэтому у любого запроса источник — локальный адрес, одной проверки источника мало. Нужно отличать запрос по SSH от проксированного из интернета: прокси всегда добавляет заголовки с адресом клиента, запрос по SSH их не имеет. Доверие к заголовкам здесь только в сторону запрета: клиент не может убрать заголовки, которые nginx выставляет сам.

- ⭕ Единое правило «только изнутри сервера» для всех служебных роутов: lab (генерация продукта, эмбеддингов, картинок, пересборка вариантов), debug еды (экспорт и импорт каталога, список, лимиты, личная калорийность: запуск и сброс), debug котировок, debug бэкапа.
- ⭕ Остаются открытыми: проверка здоровья, готовности, информации о сборке и коммите (проверить, что ими не пользуется ничего, кроме выкладки; фронтенд вызывает роут коммита).
- ⭕ Табличные тесты: чужой источник — отказ; локальный источник с заголовками прокси — отказ; локальный источник без заголовков — разрешено; открытые роуты доступны всем.
- ⭕ Обновить памятки по ручным вызовам (бэкап, расчёт личной калорийности): теперь только по SSH на локальный адрес сервера.
- ⭕ Решить: нужна ли временная блокировка этих путей в nginx до выкладки кода (до неё роуты остаются открытыми).
