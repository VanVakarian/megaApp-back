## Цель
- Один приём событий на всё: телеметрия фронта MegaApp и диагностика расширения — через общий контракт и общий код.
- Источники задаются конфигом. Новый источник — несколько строк env, не код.
- У каждого источника свои: маршрут, каталог, ротация и её порог. Всё остальное — общее: контракт, авторизация, ключи.
- Для клиента доставка гарантированная: сервер явно подтверждает, сколько сохранено и что отвергнуто.
- Владелец забирает свежие данные сам, пользователей не дёргает.

## Текущая реализация (что меняем и переиспользуем)
- `internal/telemetry`: POST-приём батча событий фронта на `/api/telemetry/events`, авторизация сессией (cookie + проверка same-origin), один NDJSON-файл, ротация на 1 ГБ, асинхронная zip-архивация в `logs-archive`. Подтверждение — только HTTP-статус (204); любое невалидное событие отбрасывает весь батч. Флаг `TELEMETRY_ENABLED` (при выключении принимает и не пишет).
- `internal/platform/appendfile`: общий примитив «дозаписать + fsync + закрыть».
- Весь `/api` на проде уже проксируется nginx на бэк: **новые маршруты под `/api` не требуют правок nginx**, поддомен не нужен.
- Глобальный лимит тела запроса 1 МиБ; единый формат ошибок `{detail}`.
- Конфиг — только переменные окружения (`.env.prod` на сервере правится вручную, в деплой-пакет CI не входит; перед выкаткой CI прогоняет `go test ./...`).
- Диск прод-сервера: 9.4 ГБ, свободно ~2 ГБ (02.10.2026).

## Решения

### Маршруты и источники
- Единый маршрут приёма: POST на `/api/ingest/<source>`. Маршруты **создаются на старте по списку источников из конфига**, по одному на источник. Неизвестный источник — обычный 404 роутера. Имена источников не секрет (они в коде клиентов), поэтому 404 ничего не раскрывает.
- Источники сейчас: `telemetry` (логи фронта MegaApp; было `/api/telemetry/events`) и `hh-auto-otclicker` (расширение). Имя источника: строчные латиница и цифры, слова через дефис, 1–32 символа.
- Старый маршрут `/api/telemetry/events` **удаляется без алиаса**. Устаревшие вкладки/сборки фронта получат 404 и по своей же логике (4xx = пачка закрыта) сбросят накопленное: потеря лишь нескольких последних perf-замеров, допустима.
- Пакет `telemetry` упраздняется целиком: приём, валидация и записи — в новом пакете `ingest`.

### Раскладка на диске
- `DATA_DIR/ingest/<source>/`: активный файл `<source>-<время открытия>.ndjson`; закрытые уезжают zip-архивами в `logs-archive` внутри того же каталога источника. Телеметрия и расширение изолированы целиком: свои файлы, свои архивы, своя ротация.
- Старые файлы `frontend-telemetry-*.ndjson` и `logs-archive` в корне `DATA_DIR` остаются как есть (старый формат с полями на верхнем уровне, новый — с вложенными `data`; смешивать их в одной серии нельзя). Владелец сам архивирует или удаляет их, когда не нужны.

### Авторизация: одна на все источники
- Любой источник принимает запрос, если выполняется **одно из двух**; иначе отказ. Настроек авторизации у источника нет.
- **Ключ** — заголовок `X-Ingest-Key` совпадает с одним из ключей общего списка. Для внешних клиентов без пользователя (расширение). Same-origin не проверяется (Origin service worker расширения — `chrome-extension://`).
- **Сессия** — cookie-сессия и проверка same-origin, как у остального API. К записи сервер добавляет id пользователя. Для фронта MegaApp.
- Сначала проверяется ключ; не подошёл — сессия. Нет ни того, ни другого — 401 (чужой Origin при сессии — 403).
- Для ключа обязательны **ключ в заголовке, а не в адресе** (адреса попадают в access-лог nginx), сравнение за постоянное время, HTTPS, ключ только в `.env.prod` и в настройках клиента (не в гите), ответ 401 без деталей.
- **Скрывать роут не нужно:** он виден в манифесте расширения и в гите, секретом быть не может. Безопасность — на ключе.
- **Формат ключа:** сгенерированный случайно, 32 символа, латиница обеих регистров и цифры (~190 бит). Спецсимволы стойкости не прибавляют, но ломают env-строки и заголовки. Конфиг отвергает ключ короче 24 символов или с посторонними символами.
- **Ротация ключа без простоя:** в списке допускается несколько ключей; добавить новый, обновить клиента, убрать старый.
- Не `JWT_SECRET` и не пользовательская сессия для внешних клиентов.
- Rate-limit на проваленные ключи не делаем (перебор 190 бит бессмыслен; без ключа ничего не пишется на диск). Если появится шум — лимит в nginx.

### Конфигурация (главный вопрос плана)
Принцип: **две переменные на весь приём; у источника нет ничего, кроме имени и порога ротации; любая опечатка — ошибка на старте**.

**Схема переменных:**
| Переменная | Смысл | Умолчание |
|---|---|---|
| список источников | пары «имя:порог» через запятую, порог у каждого указан явно; пусто = приём выключен целиком, маршрутов нет | пусто |
| ключи | общий список ключей через запятую, годятся для любого источника; пусто = внешние клиенты не проходят, только сессии | пусто |

- Пример прода: `INGEST_SOURCES=telemetry:1GB,hh-auto-otclicker:100MB` и `INGEST_KEYS=<сгенерированный ключ>`. Добавить источник = дописать пару; убрать = убрать пару.
- Порога по умолчанию и перекрытия нет: у каждого источника свой, явный. Ветвлений «взять общий, если не задан» нет.
- **Формат порога:** целое число с необязательной единицей `KB`/`MB`/`GB` (десятичные: 1 МБ = 10^6 байт, как и принято в проекте для «1 ГБ»); просто число — байты. Минимум 1 МБ (меньше потолка батча — ротация на каждой записи).

**Строгая проверка на старте (отказ запуска с понятным сообщением, значения ключей в сообщения не попадают):**
- каждая запись списка источников — «имя:порог»; имена валидны и не повторяются;
- порог парсится и не меньше минимума;
- любая другая переменная приёма — ошибка (ловит опечатки и остатки прежней схемы с переменными на источник);
- ключи корректны (длина, символы) и не повторяются.

**Прозрачность:** на старте одна строка лога на источник — имя, порог, каталог; ключи не логируются.

**Менять конфиг:** правка `.env.prod` + рестарт сервиса (как для всего конфига бэка). Ротация ключа, смена порога у `telemetry` (например, понизить с 1 ГБ, если диск жмёт) — без выкатки кода.

**Рассмотрено и отвергнуто:**
- режим авторизации и ключи на каждый источник (первая реализация): лишние переменные, и для телеметрии пришлось задавать отдельную строку; контракт перестаёт быть единым;
- общий порог с перекрытием на источник: ветвление «задан свой или нет»;
- одна переменная-JSON — экранирование в env, секреты внутри JSON;
- конфиг-файл (в гите или встроенный в бинарь) — новый механизм в проекте, где всё на env, и правка порога требовала бы выкатки.

### Подтверждение доставки
- Сервер отвечает **подсчётом**: получено, сохранено, отвергнуто (список с причинами). Сохранено = записано и `fsync`-нуто до ответа.
- **Невалидное событие отвергается само, не весь батч** (в плане 36 было наоборот). Одна битая запись не блокирует очередь клиента.
- Инвариант: сохранено + отвергнуто = получено. Клиент его проверяет (расширение — строго; фронт — достаточно статуса 200).
- Гарантия «как минимум раз»: id события устойчив; при потерянном ответе повтор даст дубль строки. Сервер не дедуплицирует (нужен постоянный индекс id, сложнее и тоже ломается); читатель схлопывает по одному `id`. Поэтому **`id` обязан быть уникален в пределах источника сам по себе**, без опоры на `X-Client-ID` (у `sendBeacon` заголовка нет, и копии одного события приходят с разным клиентом): фронт — случайный идентификатор вкладки + номер, расширение — идентификатор установки + журнал + время + хеш.
- Батч пишется одним вызовом дозаписи с одним `fsync` под мьютексом источника; хвост файла после падения процесса может содержать оборванную строку, читатель такие пропускает.

### Ротация
- Писатель с ротацией — **общий платформенный пакет** (по образцу `appendfile`), параметры: каталог, префикс, порог. Один экземпляр на источник со своим порогом.
- По достижении порога: закрыть файл с меткой времени, начать новый, закрытый — в zip в `logs-archive`, исходник удалить. Файл не превышает порог (запись, которая не влезает, открывает новый файл).
- Доработка при выносе (надёжность): после падения процесса между закрытием и архивацией «закрытый, но не заархивированный» файл остаётся навсегда. Писатель при первой записи после старта доархивирует такие. Zip пишется во временное имя и переименовывается — полуфайл не выглядит готовым.
- Архивы автоматически не чистятся; чистка — вручную владельцем (автоочистка — отдельный план, если понадобится).

### Выдача данных владельцу
- Файлы лежат в `DATA_DIR/ingest/<source>/` на проде; забираются `rsync`/`scp` на Mac и разбираются через `jq`/скрипты. Эндпоинта чтения нет: доступ к серверу закрывает задачу, лишний HTTP-вход — лишняя поверхность.

## Контракт v1

### Запрос
- POST на `/api/ingest/<source>`, тело JSON.
- Заголовки: `X-Ingest-Key` (ключ) либо cookie сессии — достаточно одного. `X-Client-ID` — идентификатор клиента, **необязательный** (у `sendBeacon` фронта заголовков нет): 1–64 символа, латиница, цифры, дефис, подчёркивание; нет заголовка или значение не подходит — пишется пустым (кривой заголовок не повод отказать в событиях, это 400 не вызывает). Расширение шлёт всегда.
- Тело — объект: список событий (1–1000) и необязательное целое «потеряно клиентом до этого батча» (≥ 0). Весь запрос не больше 512 КиБ.

### Событие
| Поле | Тип | Правила |
|---|---|---|
| идентификатор | строка 1–128 | уникален в пределах клиента; одинаков при повторной отправке той же записи |
| поток | строка 1–64 | строчные латиница, цифры, точка, дефис, подчёркивание; смысловая «таблица» источника |
| время | целое > 0 | миллисекунды Unix, когда событие случилось на клиенте |
| данные | объект JSON | произвольное содержимое; не больше 64 КиБ на событие |

- Прочие поля события игнорируются, не сохраняются: служебные поля клиент подменить не может.
- Данные сервер не интерпретирует и не перекодирует.

### Ответ
- **200** — запрос обработан (даже если часть событий отвергнута). Тело: получено, сохранено, список отвергнутых; элемент — индекс события, машинный код причины, короткий текст. Коды: не объект, плохой идентификатор, плохой поток, плохое время, плохие данные, слишком большое событие.
- **400** — запрос в целом негоден (не JSON, нет списка, пуст, больше 1000, отрицательный счётчик потерянных). Решение, что делать, за клиентом: расширение пачку не трогает и сообщает об ошибке, фронт по своей логике «4xx — закрыто» сбрасывает.
- **401** — нет ни верного ключа, ни действующей сессии.
- **404** — источник не сконфигурирован.
- **413** — тело больше лимита; клиент уменьшает пачку.
- **5xx** — сбой записи или бэка (в том числе рестарт при деплое); клиент ничего не считает доставленным.
- Ошибки 4xx/5xx — в общем формате ошибок бэка.

### Имена полей на проводе
- Запрос: `events` (список), `dropped` (число, необязательное). Событие: `id`, `stream`, `at`, `data`. Заголовки: `X-Ingest-Key`, `X-Client-ID`.
- Ответ 200: `received`, `stored`, `rejected` (всегда список, при отсутствии отказов пустой, не `null`); элемент отвергнутого: `index`, `code`, `message`.
- Коды причин: `not_an_object`, `bad_id`, `bad_stream`, `bad_at`, `bad_data`, `too_large`.
- Строка в файле: `receivedAt`, `source`, `client`, `user` (только если запрос прошёл по сессии), `droppedBefore` (только у первого сохранённого события батча и только если `dropped` > 0), `id`, `stream`, `at`, `data`.

### Что хранится
- Одна строка NDJSON на принятое событие: серверное время приёма (UTC), источник, клиент, пользователь (только если запрос прошёл по сессии), затем идентификатор, поток, время и данные клиента; у первого сохранённого события батча — счётчик «потеряно до батча», если задан. Серверные поля клиент задать не может.
- Потоки одного источника лежат вперемешку в серии файлов источника; различаются полем «поток» (`grep`/`jq`).

## Изменения в бэке
- Общий писатель с ротацией (вынос из `telemetry`), параметры, доархивация осиротевших, временное имя zip; тесты (перенос существующих).
- Новый пакет `ingest`: реестр источников из конфига, регистрация маршрута на источник, одна проверка «ключ или сессия» для всех, разбор/валидация конверта, подсчёт-ответ, запись. Сессия проходит через существующее промежуточное звено авторизации (с same-origin); ключ проверяется до него и same-origin не требует.
- Конфиг: разбор схемы выше, строгая проверка, строка лога на источник; удаляется флаг `TELEMETRY_ENABLED` и его поле.
- Подключение в сборке приложения вместо `telemetry`; пакет `telemetry` удаляется.
- `.env.prod.example` / `.env.test.example`: новые переменные с плейсхолдерами (без реальных ключей), удалён старый флаг.
- Тесты (`testing`, таблицы, `httptest`, временные каталоги): валидность каждого кода причины, смесь валидных и невалидных, оба способа входа на каждом источнике (верный/неверный/пустой ключ, нет сессии, same-origin только для сессии), 400/401/404/413, инвариант ответа, ошибка записи → 5xx, ротация на малом пороге **с разными порогами у двух источников в одном процессе**, доархивация осиротевшего, все правила строгой проверки конфига (каждая — отдельный случай с понятным сообщением), опечатка в имени переменной.
- Проверки: сборка в `bin/`, `go vet`, `go test ./...` (CI гоняет их перед деплоем).

## Риски и допущения
- **Диск:** по решению владельца у `telemetry` порог остаётся 1 ГБ (рядом с активным файлом при архивации лежит ещё и zip-копия). Порог меняется без выкатки кода правкой пары в списке источников; для расширения 100 МБ — при ~0.3–0.5 МБ/сутки это месяцы.
- Дубли при потерянном ответе — принятая цена; читатель схлопывает по `id` (он уникален в источнике).
- Утечка ключа: ротация без простоя; сам по себе ключ даёт лишь писать мусор в файлы источников (чтения нет).
- Разный формат старых и новых файлов телеметрии (плоские поля / вложенные `data`): старые файлы остаются отдельно; скрипты разбора должны знать оба формата, пока старые нужны.
- **Старые файлы телеметрии сами не архивируются и не удаляются** (новый код в корень `DATA_DIR` не заглядывает): их нужно доархивировать вручную после выката (шаг 7), иначе они навсегда останутся несжатыми и займут место на диске с ~2 ГБ свободных.
- Пользовательская телеметрия фронта привязана к пользователю (идёт по сессии), как и раньше.
- Оборванная последняя строка после падения: читатель пропускает невалидные строки.

## Не входит
- Приём бинарных данных (картинки капч) — позже отдельным маршрутом, контракт v1 не расширяется.
- Чтение/выдача по HTTP, автоочистка архивов, дедупликация на сервере, лимитер.

Область ревью: megaapp-back и megaapp-front (план 42 в обоих). Другого найдено не было.

1. Оборванная запись остаётся в файле и «склеивается» со следующим пакетом
   - **Важность:** стоит поправить
   - **Как сейчас работает:** сервер дописывает пачку событий в конец файла и подтверждает клиенту, что всё записано, только если запись прошла целиком. Если запись упала на полпути (например, кончилось место на диске), сервер отвечает ошибкой, и клиент оставляет события у себя, чтобы прислать позже.
   - **Что не так:** обломок, успевший записаться до сбоя, остаётся в конце файла без перевода строки. Когда место появляется и клиент присылает те же события повторно, первая строка нового пакета дописывается прямо к обломку и получается одна нечитаемая строка. Сервер говорит «сохранено», клиент стирает события у себя, а одно из них в файле уже не прочитать. Свободно на диске сервера около 2 ГБ, так что сценарий реален, хоть и редок. Плюс часть событий, дошедших до сбоя, при повторе окажется записанной дважды.
   - **Как поправить:** перед записью запоминать размер файла; при любой ошибке записи возвращать файл к этому размеру (обрезать), а если не получилось, закрывать его и открывать новый файл.
   - **Как будет работать после правки:** сбой записи не оставляет в файле мусора, следующий пакет ложится в чистое место, всё, что сервер подтвердил, действительно читается.

Второй проход (после перехода на единый контракт «ключ или сессия», 02.10.2026): код приёма и конфига замечаний не вызвал, найдено одно по стыку с фронтом.

2. Дубли от `sendBeacon` не схлопываются правилом «клиент + id»
   - **Важность:** мелочь, но стоит поправить
   - **Источник:** Claude
   - **Как сейчас работает:** при закрытии вкладки фронт отправляет остаток очереди через `sendBeacon`, а саму очередь не чистит (ответа он не увидит). Те же события при следующем открытии уходят обычным запросом. Сервер дубли не отсеивает, читатель по плану схлопывает их по паре «клиент + id».
   - **Что не так:** `sendBeacon` не умеет заголовки, поэтому у его копии клиент пустой, а у обычной отправки — с идентификатором устройства. Пары разные, и одно и то же событие считается двумя: счётчики и средние по замерам после каждого закрытия вкладки с непустой очередью чуть завышены.
   - **Как поправить:** схлопывать читателем по одному `id` (он вида «сессия:номер», уникален сам по себе) либо класть идентификатор клиента в тело beacon.
   - **Как будет работать после правки:** копии одного события из beacon и из обычной отправки считаются одним.
