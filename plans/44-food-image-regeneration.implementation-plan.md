# 44. Перегенерация картинок еды (основной план, бэк)

Парный план фронта: `megaapp-front/plans/44-food-image-regeneration.implementation-plan.md`. Номер, имя и коммиты `[044]` общие для обоих репозиториев.

## Цель

Администратор может перегенерировать любой продукт без картинки или с плохой картинкой одним нажатием в форме редактирования. Провал генерации больше не бывает тихим: пользователь и лог видят результат.

## Текущая архитектура

- Генерация запускается только при создании продукта. Правка и повторное сохранение её не запускают.
- Очередь в памяти процесса: до 24 задач, один воркер, пауза секунда между задачами, 3 попытки с паузами 1 и 2 секунды, таймаут 2 минуты на попытку. Дубль по одному продукту схлопывается.
- Продукт с готовой картинкой пропускается молча. Полная очередь, отсутствие генератора и окончательный провал — только строка в логе сервера.
- Результат — оригинал и пять вариантов на диске. Номер версии растёт на единицу, старые файлы удаляются. Версии держатся в памяти, при старте читаются с диска.
- По успеху всем клиентам уходит событие «картинка готова». События о провале нет.
- Версия каталога (сигнал «каталог изменился» для догонки после реконнекта) при генерации картинки не растёт. Каталог в кеше хранится без номеров версий картинок, они подставляются свежими при каждом чтении.
- Отдельный лабораторный маршрут умеет генерировать картинку, но только для продукта без картинки, синхронно, через GET.
- Маршруты лаборатории и отладки зарегистрированы без авторизации.

## Найденные проблемы

Расследование на проде (10.10.2026, только чтение):

- У продуктов «Желток» и «Салат Цезарь с креветками» нет ни одного файла картинки, ни оригинала, ни вариантов. Сервер отдаёт их без номера версии, фронт без него не рисует картинку и не делает запросов, поэтому в консоли и сети пусто. Остальные 454 из 456 продуктов с картинками.
- «Желток» создан в апреле 2026, его генерация провалилась и никогда не повторялась: повтор не предусмотрен. В журнале сервера более ранних записей нет, причину сбоя установить нельзя.
- Провал генерации молчаливый: пользователь узнаёт о нём только по отсутствию картинки. Полная очередь отбрасывает задачу так же молча.
- Паузы между попытками в секунду-две слишком короткие для лимитов провайдера: три попытки укладываются в несколько секунд.
- Клиент, пропустивший событие «картинка готова» (вкладка в фоне, обрыв сокета), не узнаёт о картинке до полной перезагрузки: версия каталога не менялась, догонка ничего не скачает.
- Без ключа провайдера в генератор попадает «пустой, но не nil» объект. Проверка «генератор не настроен» не срабатывает, воркер падает и роняет процесс.
- Маршруты лаборатории и отладки открыты в интернете без авторизации: nginx проксирует весь `/api`, анонимные запросы к ним возвращают 200. Среди них экспорт и импорт каталога, сброс персональных калорий, платные вызовы провайдера. Фронт этими маршрутами не пользуется, они нужны только для работы с сервера.

## Решение

### Единый вход в генерацию

Пайплайн принимает запрос генерации с признаком «заменить существующую». Создание продукта — запрос без замены, кнопка — с заменой. Всё остальное (очередь, попытки, запись файлов, события) общее.

- Замена не удаляет старую картинку заранее. Старые файлы убираются только после успешной записи новой, как сейчас при смене версии. Провал оставляет прежнюю картинку.
- Дубль запроса по продукту, который уже в очереди, не создаёт второй задачи. Ответ говорит, что задача уже стоит.
- Признак замены не влияет на уже поставленную обычную задачу: одна задача на продукт.

### Маршрут перегенерации

Новый авторизованный маршрут только для администратора: генерация платная, и право на неё то же, что у архивирования продуктов. Проверка администратора переиспользует ту, что уже есть у каталога для архивного флага, отдельного механизма не заводится. Метод — POST на ресурс продукта.

- Ответ 202 сразу, результат приходит событием. Генерация длится секунды, держать соединение незачем.
- Ошибки: не администратор — 403; продукт не найден — 404; генерация выключена (нет ключа) — отдельная понятная ошибка; очередь полна — 429. Тихих пропусков не остаётся.
- Проверка прав идёт раньше всего остального, как у архивного флага.
- Идемпотентность не нужна: повтор схлопывается очередью.
- Структура модуля та же, что у остального каталога: обработчик отвечает за HTTP, сервис — за проверки и постановку в очередь.

### Видимый провал

- После окончательного провала всем клиентам уходит событие «картинка не удалась» с номером продукта. Фронт по нему снимает состояние «генерируется» и показывает ошибку.
- Событие уходит и для провала при создании продукта: клиент, у которого открыта форма, увидит тот же результат.
- Лог окончательного провала остаётся, в него добавляется причина последней попытки.

### Паузы между попытками

Паузы растут до порядка секунд-десятков секунд (например 5 и 20), чтобы пережить кратковременный лимит провайдера. Число попыток остаётся настройкой. Точные значения — по опыту работы после выкладки.

### Версия каталога при готовой картинке

Готовая картинка поднимает версию каталога. Клиент, пропустивший событие, на следующей догонке увидит другую версию и скачает каталог заново.

- Поднимается только счётчик версии. Кеш каталога и индекс поиска не сбрасываются: в кеше нет номеров картинок, а поиск от картинок не зависит.
- Для этого у кеша каталога появляется отдельная операция «только поднять версию».

### Единая точка проверки генератора

В пайплайн всегда передаётся либо рабочий генератор, либо явное «нет генератора». «Пустой, но не nil» объект больше не возможен. Маршрут перегенерации и создание продукта используют одну и ту же проверку.

### Обзор продуктов без картинки

При старте сервис пишет одну предупреждающую строку со списком номеров продуктов без картинки (архивные не считаются). Автоматической генерации нет: она тратит деньги и не должна запускаться сама.

### Лаборатория и отладка — только с сервера

Маршруты лаборатории и отладки доступны исключительно локально, с самого сервера (curl по SSH). Из интернета — никак, ни с сессией, ни без. Образец — защита записывающих маршрутов во Flatline: проверка источника запроса как middleware на группе маршрутов, отказ 403 с тем же видом ответа.

- Единая группа маршрутов с одним middleware, а не проверка в каждом обработчике. Новые маршруты в группе закрыты по умолчанию. Список разрешённых адресов (настройка из окружения, как у Flatline) не нужен: допускается только сервер, то есть только локальные адреса.
- Отличие от Flatline, обязательное. Flatline проверяет «сырой» адрес TCP-соединения, а не заголовки, потому что заголовки подделываются. Но Flatline слушает наружу, а у бэкенда перед носом nginx на том же сервере: адрес соединения у всех запросов, и внешних, и серверных, один — локальный. Одной проверки адреса поэтому мало, она пропустила бы весь интернет.
- Что отличает серверный вызов от пришедшего через nginx: nginx ко всем запросам `/api` принудительно ставит заголовок с адресом клиента (значение клиента затирается) и дописывает цепочку адресов. Серверный вызов напрямую на порт бэкенда этих заголовков не имеет. Правило: допускается запрос с локального адреса соединения и без заголовков прокси; наличие любого из них — отказ.
- Адрес, который подставляет общий middleware «реальный IP» в роутере, для проверки не используется: он берёт клиента из заголовков, включая те, что nginx не затирает и которые клиент может прислать сам, поэтому через него можно выдать себя за локальный адрес. Проверка смотрит на адрес самого соединения и на наличие заголовков, не на подставленное значение.
- Если nginx перестанут ставить эти заголовки, защита сломается незаметно (откроется наружу). Поэтому тест фиксирует поведение на запросе с заголовками прокси, а в конфиге nginx они остаются обязательными (запрет префиксов в nginx как второй слой — в идеях на будущее).
- Обёртка не зависит от авторизации и сессий: серверные вызовы идут без куки.
- Отказ — 403, как у Flatline, тело в обычном для проекта виде ответа с ошибкой.
- Публичный маршрут сведений о коммите (его читает фронт при старте) остаётся открытым и в группу не входит.
- Рассмотрено и отброшено: второй сервер на отдельном локальном порту только для лаборатории и отладки. Надёжнее по построению, но лишний сервер со своим запуском и остановкой при одном потребителе — перебор.
- Лабораторная генерация картинок удаляется: её заменяет маршрут перегенерации. Пересборка вариантов из оригинала остаётся как диагностика.
- Фронт лабораторные и отладочные маршруты не использует (кроме публичного маршрута сведений о коммите), закрытие его не затрагивает.

### Не меняется

- Очередь остаётся в памяти. Потерянную рестартом задачу пользователь повторяет кнопкой.
- Промпт, модель, набор вариантов, правила именования файлов, отдача картинок.
- Создание продукта: порядок «сохранить, потом поставить в очередь».

## Находки после ревью (v-review:claude, 10.10.2026)

Ревью покрыло оба репозитория (план парный, файлы указаны с именем репозитория).

1. Кнопка блокируется на 8 минут, если сервер потерял задачу
   - **Важность:** стоит поправить
   - **Как сейчас работает:** после нажатия фронт помечает продукт «генерируется» и ждёт событие «готово» или «не удалось»; если события нет, состояние снимается запасным таймером через 8 минут.
   - **Что не так:** очередь на сервере живёт в памяти. Если сервер перезапустится (например, деплой) сразу после нажатия, задача пропадёт, событий не будет, и кнопка будет заблокирована до конца таймера. Переподключение сокета состояние не сбрасывает.
   - **Как поправить:** сбрасывать состояние «генерируется» при переподключении сокета (после реконнекта результат всё равно мог быть потерян), либо запрашивать у сервера, стоит ли ещё задача в очереди.
   - **Как будет работать после правки:** после рестарта сервера кнопка быстро становится доступной, и можно нажать снова.

2. Построение адреса миниатюры теперь в двух местах
   - **Важность:** мелочь, но стоит поправить
   - **Как сейчас работает:** список выбора (`megaapp-front/.../food-product-picker.ts`) и новый метод сервиса каталога каждый строят адрес миниатюры по своей копии формата.
   - **Что не так:** при смене схемы имён файлов легко поменять одно место и забыть второе, миниатюры в списке и в форме разойдутся.
   - **Как поправить:** список выбора берёт адрес из метода сервиса каталога.
   - **Как будет работать после правки:** формат адреса в одном месте.

3. Мёртвый код в пайплайне после удаления лабораторной генерации
   - **Важность:** мелочь, но стоит поправить
   - **Как сейчас работает:** в `megaapp-back/internal/food/image_pipeline.go` остались тип записи каталога для картинок и функция сортировки таких записей; нигде не используются.
   - **Что не так:** лишний код и ради него подключённый пакет сортировки.
   - **Как поправить:** удалить тип, функцию и ставший ненужным импорт.
   - **Как будет работать после правки:** поведение то же, файл короче.

4. Закрытие лаборатории и отладки держится на заголовках nginx
   - **Важность:** стоит поправить
   - **Как сейчас работает:** запрос считается серверным, если у него нет заголовков прокси (`X-Real-IP`, `X-Forwarded-For`, `True-Client-IP`) и соединение локальное; nginx сейчас эти заголовки ставит всегда.
   - **Что не так:** если кто-то уберёт эти строки из конфига nginx, запросы снаружи начнут приходить без заголовков с локального адреса и пройдут проверку: защита молча откроется. Тесты этого не ловят, они не видят конфиг nginx.
   - **Как поправить:** сделать проверку не «нет заголовков», а явное разрешение (например, отдельный локальный порт или секрет-заголовок, который nginx не пропускает), либо добавить запрет префиксов в самом nginx как второй слой и записать это в заметки по серверу.
   - **Как будет работать после правки:** случайная правка nginx не открывает лабораторию наружу.

5. Лишняя перекачка каталога после каждой готовой картинки
   - **Важность:** мелочь, но стоит поправить
   - **Как сейчас работает:** при готовой картинке версия каталога растёт; клиент, уже применивший событие, свою локальную версию не обновляет.
   - **Что не так:** при следующей синхронизации клиент видит расхождение версий и скачивает весь каталог (~456 записей), хотя ничего не изменилось.
   - **Как поправить:** вместе с событием «картинка готова» передавать новую версию каталога, клиент записывает её после применения.
   - **Как будет работать после правки:** каталог перекачивается только тем, кто событие пропустил.

6. Проверка продуктов без картинки при старте без ограничения по времени
   - **Важность:** мелочь, но стоит поправить
   - **Как сейчас работает:** при запуске сервер читает каталог из БД ради одной строки в логе; ограничения по времени у чтения нет.
   - **Что не так:** при медленной или залипшей БД запуск (и деплой) ждёт эту проверку, которая не нужна для работы.
   - **Как поправить:** запускать проверку с коротким таймаутом или в фоне после старта.
   - **Как будет работать после правки:** запуск не зависит от проверки.
