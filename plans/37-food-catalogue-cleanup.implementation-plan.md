# 37. Чистка каталога продуктов

Источник: анализ прод-БД (`vps-31`, read-only), дата анализа 2026-10-01.
Объём на момент анализа: 473 продукта в каталоге, 50 443 записи дневника, 3 пользователя, каталог общий.

Обозначения:
- `id N` — идентификатор продукта в каталоге.
- `N зап.` — число записей дневника с этим продуктом (`0 зап.` — продукт ни разу не использован).
- `N ккал`, БЖУ — на 100 г продукта.
- Число внутри «…» — часть имени продукта.
- `␠` — пробел в конце имени.
- Этап 1: число записей до слияния. Этапы 2–5: текущее, после слияния.

## Цель

Убрать унаследованные дубли и склейки по калорийности (остались от старой kcal-only системы). Каталог: один продукт = одна сущность.

## Контекст

- Каталог глобальный, уникальность только по точному имени (чувствительно к пробелам и регистру) → дубли с пробелом в конце.
- Слияние = перепривязка записей дневника и персональной истории ккал (уникальна по пользователь+продукт+месяц: при пересечении побеждает оставляемый продукт). Версию записи дневника не трогаем: клиент заменяет данные дня целиком.
- Кэши каталога, поиска и статистики живут в памяти сервера → на время правки БД сервис останавливается.
- Версия каталога (`catalogue/version`) хранится в памяти, после рестарта равна 0 → клиенты с сохранённой версией 0 могут не перекачать каталог. Устойчивая к рестарту версия: отдельная правка кода.
- Картинки лежат по id продукта; файлы удалённых продуктов остаются на диске.
- Метод правки данных: SQL-скрипты в `data-fixes/`, одна транзакция с проверками внутри, независимый верификатор против копии «до».
- У продуктов есть эмбеддинги имени и описания (семантический поиск) + кэш эмбеддингов запросов. Переименование/слияние/смена описания → пересчёт.
- Разделение склеенного продукта историю не разделит: старые записи неразличимы. Нужно решение, куда их отнести.
- Прогонять сначала на копии прод-БД.
